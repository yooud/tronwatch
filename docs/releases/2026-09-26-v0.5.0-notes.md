## Highlights

TronWatch v0.5.0 can resume its persisted canonical chain after downtime without running a full TRON node. Historical synchronization is bounded, uses one peer as the active sync leader, and can fail over to another eligible peer while live pending transactions continue flowing.

## Upgrade Notes

- Existing databases and configurations require no manual migration.
- Catch-up remains resume-only: an empty database starts from live traffic instead of downloading the chain from genesis.

## Product Areas

### P2P synchronization

- Added: bounded historical block synchronization resumes from the persisted canonical tip after downtime.
- Added: a failed sync leader can be replaced by another eligible peer without merging peer streams into duplicate processing.
- Changed: readiness stays false until the persisted tip is explicitly confirmed at the remote head.

### Operations and observability

- Added: catch-up progress, failures, peer selection, and chain gaps are exposed through logs and Prometheus metrics.
- Added: configuration controls batch size and per-request timeout.
- Changed: readiness now accounts for active catch-up and unresolved chain gaps.

### Build and supply chain

- Changed: Go runtime dependencies were updated and verified against the complete test suite.
- Changed: GitHub checkout and Go setup actions were updated to their current pinned releases.
- Changed: the release SBOM action was updated while retaining immutable action pins.

## Known Issues

- Replayed blocks use the watchlist active at processing time, so catch-up does not retrospectively index targets added after the original block time.
- A peer whose retained history starts after the persisted tip cannot serve as the catch-up leader.
